# 龙渊 / 勇士深渊 波次机制分析与修复方案

> 针对两个反馈：
> 1. 进入 BOSS 波后会**先出一遍 BOSS 波的鼠军**，然后 BOSS 才登场。
> 2. **只有 1 只敌人的超短波，实际耗时很长**，导致关卡时间被拖长；勇士深渊同样如此。
>
> 本文只做分析与方案，不含改动。

---

## 0. TL;DR

| 现象 | 直接原因 | 代码位置 | 修法 |
|---|---|---|---|
| BOSS 波先出鼠军 | BOSS 必须等「本波最后一个 subwave 出完 **且** 场上敌人全清」才召唤 | `objects/obj_battle/Step_0.gml:348`、`objects/obj_battle/Step_2.gml:106-118` | 让龙渊/勇士深渊的 BOSS 与本波第一个 subwave 同时登场 |
| 1 只敌人的波也要拖很久 | 每个 subwave 固定 `wave_max_time`（龙渊 1500 帧、勇士深渊 900 帧），快进的三个条件互相卡死 | `objects/obj_battle/Create_0.gml:233-262`、`objects/obj_battle/Step_2.gml:41-64` | 修 `current_total_hp` 口径 + 按敌人数动态缩放下限 + 清场即推进 |
| 关卡总时长夸张 | 龙渊 631 个 subwave、勇士深渊 285 个 subwave，逐个累加 | 关卡 json | 上述代码修复后自然下降；可选再砍 BOSS 波 subwave 数 |

三个缺陷叠加，最坏情况下龙渊 6 关合计要 4.4 小时、勇士深渊一关 1.97 小时才能打完。

## 1. 波次状态机（完整还原）

### 1.1 状态与变量

| 变量 | 位置 | 含义 |
|---|---|---|
| `level_stage` | `obj_battle/Create_0.gml:217` | `"ready"` 开场 → `"pre"` 出怪 → `"boss"` BOSS 阶段 → 死亡回 `"pre"` |
| `current_wave` / `current_subwave` | `Create_0.gml:215` | 当前大波 / 当前小波（subwave） |
| `wave_timer` | `Create_0.gml:228` | 当前 subwave 的倒计时（帧） |
| `wave_max_time` / `wave_min_time` | `Create_0.gml:226-227` | 默认 25 秒 / 4 秒 |
| `current_wave_max_time` | `Create_0.gml:241` | 本 subwave 的初始时长，用于算快进阈值 |
| `current_total_hp` | `Create_0.gml:246` | 本 subwave 的**总血量**（快进判定基准） |
| `current_wave_hp` / `current_wave_alive_count` | `Step_2.gml:31-40` | 场上存活敌人血量之和 / 数量 |
| `boss_waiting_clear` | `Create_0.gml:243` | BOSS 待召唤标记 |
| `time_ticks_this_step` | `Step_0.gml:197` | 本帧推进的 tick 数（通常 1） |

### 1.2 时间参数来源（`Create_0.gml:226-239`）

```gml
wave_max_time = 25*60          // 25 秒
wave_min_time = 4 * 60         // 4 秒
if global.difficulty >= 3 && global.map_id != "tower_cake"{
    wave_max_time = 12.5*60    // 难度 3+ 减半
}
if is_real(global.level_file.version){
    wave_max_time = global.level_file.max_wave_time
    wave_min_time = global.level_file.min_wave_time
    if global.difficulty >= 3 && global.map_id != "tower_cake"{
        wave_max_time = round(wave_max_time/2)
    }
}
```

- 龙渊 6 关：`max_wave_time: 1500`、`min_wave_time: 240` → 25 秒 / 4 秒
- 勇士深渊：`max_wave_time: 900`、`min_wave_time: 240` → 15 秒 / 4 秒
- 难度 3+（美味之上）再减半

### 1.3 每个 subwave 的推进（`Step_0.gml:337-361`）

```gml
if wave_timer <= 0 && level_stage == "pre"{
    if !boss_waiting_clear {
        ...
        if current_wave < total_wave{
            enemy_subwave_summon()          // 一次性生成整个 subwave
        }
        if current_subwave < current_total_subwaves-1{
            current_subwave+=1
        }
        else if current_wave < total_wave{
            if wave_data.boss_wave && (...){
                boss_waiting_clear = true   // ← 问题 1 的起点
            }
            else{
                current_wave += 1
                current_subwave = 0
                ...
            }
        }
    }
}
```

`enemy_subwave_summon()`（`Create_0.gml:245-426`）在**一帧内**把整个 subwave 的敌人全部实例化，没有逐只延迟。所以「出怪」本身是瞬时的，真正占时间的是 `wave_timer` 倒计时。

### 1.4 倒计时与快进（`Step_2.gml:41-64`）

```gml
var c_min_time = wave_min_time                     // 下限，默认 240
if is_real(version) && version >= 1.3 {
    if (...local_min_wave_time > 0) c_min_time = local_min_wave_time
}
if current_wave_hp <= hp_ratio * current_total_hp && level_stage != "boss"{
    if current_wave_max_time > c_min_time{
        if wave_timer < (current_wave_max_time - c_min_time) && wave_timer > 30{
            wave_timer = 30                        // 快进到 0.5 秒
        }
    }
}
if not global.is_paused{
    wave_timer -= obj_battle.time_ticks_this_step
}
```

快进要**同时**满足四个条件：

1. `current_wave_hp <= hp_ratio * current_total_hp` —— 场上血量降到阈值
2. `level_stage != "boss"`
3. `wave_timer < current_wave_max_time - c_min_time` —— **已经过去至少 4 秒**
4. `wave_timer > 30` —— 还没到 0.5 秒以内

即：**一个 subwave 的最短生命周期 = `c_min_time`（4 秒）+ 30 帧（0.5 秒）= 4.5 秒**，跟这一波有 1 只敌人还是 30 只敌人完全无关。

## 2. 问题 1：BOSS 波先出鼠军

### 2.1 触发链

```
wave_timer 到 0
  → Step_0.gml:342   enemy_subwave_summon()      // 出本波最后一个 subwave
  → Step_0.gml:348   boss_wave 为真 → boss_waiting_clear = true
  → Step_2.gml:106   每帧检查：必须 current_wave_alive_count == 0 才保持该标记
  → Step_2.gml:116   boss_waiting_clear && current_wave_alive_count == 0
  → level_stage = "boss"，生成 BOSS
```

三个前置条件缺一不可：

1. 已推进到本波**最后一个** subwave（`current_subwave >= total_subwaves - 1`）
2. 该 subwave 的 `wave_timer` 已经走完
3. 场上存活敌人数量为 **0**

### 2.2 实测「BOSS 波」的规模

| 关卡 | BOSS 波位置 | subwave 数 | 鼠军总数 | BOSS |
|---|---|---|---|---|
| longyuan_1_hard | w4 | 5 | 80 | ly_youshen |
| longyuan_2_hard | w4 | 5 | 96 | ly_youshen |
| longyuan_3_hard | w4 / w6 / w8 | 5 ×3 | 114 / 133 / 130 | ly_youshen / ly_hengha / ly_diting |
| longyuan_4_hard | w4 | 5 | 127 | ly_hengha |
| longyuan_5_hard | w4 | 5 | 123 | ly_wuchang |
| longyuan_6_hard | w5 / w7 / w9 | 5 ×3 | 130 / 140 / 155 | ly_hengha / ly_wuchang / ly_mengpo |
| **abyss_warrior** | w2 / w3 / w5 | **60 ×3** | **420 / 420 / 360** | ice_residue / rumble / abyss_pharaoh |

- 龙渊：一个 BOSS 波要先打掉 80–155 只鼠
- 勇士深渊：一个 BOSS 波要先打掉 **360–420 只鼠**，且 60 个 subwave 每个至少 4 秒 → **光出怪间隔就 4 分钟**

### 2.3 为什么说是「设计缺陷」而不是「难度设计」

- BOSS 波的小怪在 `level_stage == "boss"` 之后仍会继续循环召唤（`Step_0.gml:362-370`），说明「BOSS 与小怪同场」本来就是引擎支持的
- `boss_waiting_clear` 的注释写的是「所有小怪生成完毕，等待玩家清光后再出 BOSS」，目的是**避免 BOSS 与小怪同时压场**；但对 60 个 subwave 的勇士深渊，这个等待被放大成 15 分钟以上
- 玩家体感是「BOSS 波 = 又打一遍小怪波，最后才见到 BOSS」

## 3. 问题 2：短波为什么耗时很长

### 3.1 缺陷 A：`current_total_hp` 用基础血量，与实例血量不同口径（关键）

`Create_0.gml` 生成敌人时：

```gml
var new_enemy = instance_create_depth(..., enemy_obj);   // 400
hex_enemy_scale(new_enemy);                              // 402  这里才乘上难度/海克斯倍率
...
current_total_hp += global.enemy_map[? _enemy_type].hp;  // 415  ← 用的是注册表基础值
```

`global.enemy_map[? type].hp` 是 `enemy_init` 里注册的**基础血量**，不含：

- 关卡 `hp_modify`（龙渊 1.8 / 2.0 / 2.5，勇士深渊 1.25 / 2.5）
- 难度系数
- `hex_enemy_scale()` 的海克斯倍率

而 `current_wave_hp`（`Step_2.gml:35`）累加的是**实例当前 `hp`**，是完整缩放后的值。

于是判定 `current_wave_hp <= hp_ratio * current_total_hp` 两边量纲差一个 `hp_modify` 倍。以龙渊 3 关（`hp_modify: 2.5`、`hp_ratio: 0.5`）为例：

- 实例总血量 ≈ 2.5 × 基础总血量
- 阈值 = 0.5 × 基础总血量
- 需要把实例血量打到 **0.5 / 2.5 = 20%** 才快进 —— 也就是**打掉 80% 的血**才触发

如果玩家 DPS 不够、或者怪在跑路没被打，`current_wave_hp` 一直高于阈值，**必须等满 25 秒**。

### 3.2 缺陷 B：`c_min_time` 是固定下限，与敌人数无关

`wave_min_time = 240`（4 秒）。无论这一波是 1 只还是 30 只，都必须先走完 4 秒才允许快进。于是：

- 1 只敌人的波 = 4.5 秒
- 30 只敌人的波 = 4.5 秒（只要清得快）

短波没有任何加速优势。

### 3.3 缺陷 C：清场后仍要空等

即使 `current_wave_alive_count == 0`（全场清空），`wave_timer` 仍要先满足「已过 4 秒」，再压到 30 帧，**共 4.5 秒空场等待**。

如果这一波只有 1 只敌人、出场就被秒，玩家就要对着空场等 4.5 秒。

### 3.4 缺陷 D：BOSS 阵亡后下一波没有间隔

`objects/obj_ly_boss_parent/Destroy_0.gml:18-20`：

```gml
level_stage = "pre";
current_wave += 1;
current_subwave = 0;
```

`wave_timer` 没有重置。BOSS 阶段它是 `10*60`（`Create_0.gml:250-252`）并被持续扣减，通常已经 ≤ 0，于是**下一波在 BOSS 倒地的同一帧立刻开刷**，没有喘息。

### 3.5 实测规模

| 关卡 | 波数 | subwave 数 | 敌人数 | BOSS 波 | 纯等待（按 25s/sub 上界） |
|---|---|---|---|---|---|
| longyuan_1_hard | 5 | 78 | 425 | 1 | 32 分钟 |
| longyuan_2_hard | 5 | 72 | 441 | 1 | 30 分钟 |
| longyuan_3_hard | 9 | 128 | 970 | 3 | 53 分钟 |
| longyuan_4_hard | 5 | 107 | 668 | 1 | 44 分钟 |
| longyuan_5_hard | 5 | 100 | 650 | 1 | 41 分钟 |
| longyuan_6_hard | 10 | 146 | 1254 | 3 | 60 分钟 |
| **龙渊合计** | 39 | **631** | 4408 | 10 | **263 分钟** |
| abyss_warrior | 6 | **285** | 1910 | 3 | 71 分钟（15s/sub） |
| abyss_warrior_hard | 6 | **285** | 1843 | 3 | 71 分钟 |
| abyss（普通深渊） | 9 | 69 | 566 | 3 | 17 分钟（无 max_wave_time，走 25s） |

即使每个 subwave 都「秒清」，按 4.5 秒下限计算：

- 龙渊 631 × 4.5 秒 ≈ **47 分钟**
- 勇士深渊 285 × 4.5 秒 ≈ **21 分钟**

这就是「关卡时间过长」的下限。

## 4. 修复方案

### 4.1 P0 — 修 `current_total_hp` 口径（问题 2 的核心）

`objects/obj_battle/Create_0.gml:400-415` 改为按实例血量累加：

```gml
            var new_x = global.grid_offset_x + (9 + x_offset) * global.grid_cell_size_x;
            var new_y = global.grid_offset_y + (target_row - 1) * global.grid_cell_size_y;

            var grid_pos = get_grid_position_from_world(new_x, new_y);
            var new_enemy = instance_create_depth(grid_pos.x+30, grid_pos.y + 38, 0, enemy_obj);
            hex_enemy_scale(new_enemy);

            var _hex_extra = hex_enemy_extra_chance();
            if (_hex_extra > 0 && random(1) < _hex_extra) {
                var _dup = instance_create_depth(grid_pos.x + 30 + irandom_range(-14, 14),
                                                 grid_pos.y + 38, 0, enemy_obj);
                hex_enemy_scale(_dup);
                current_total_hp += _dup.hp;          // 改：实例血量
            }

            // 改：用实例血量，而不是注册表基础值
            current_total_hp += new_enemy.hp;
```

同时 `hex_spawn_flood()`（`Create_0.gml:424`）追加的精英也要计入总血量，否则总血量再次偏小、快进更难。建议在 `hex_spawn_flood` 内每生成一只就 `current_total_hp += 实例.hp`，或在调用后重新按场上+已死敌人重算一次。

> 影响面：所有关卡。这是修正口径，让「打掉 X% 血」回到设计本意。难度越高（`hp_modify` 越大）加速越明显。

### 4.2 P0 — 最短波次时间按敌人数动态缩放（问题 2 的短波）

`objects/obj_battle/Step_2.gml`，在 `var c_min_time = wave_min_time` 之后插入：

```gml
// 本 subwave 的敌人数量决定该波的最短停留时间：
// 1 只 → 约 0.33 秒，10 只 → 3.3 秒，30 只以上封顶到 wave_min_time
var _sub_enemy_n = 1;
if current_wave < total_wave && current_subwave < current_total_subwaves {
    var _sub_list = global.level_file.waves[current_wave].subwaves[current_subwave].enemy_list;
    _sub_enemy_n = max(1, array_length(_sub_list));
}
var _dyn_min = clamp(_sub_enemy_n * 20, 20, wave_min_time);
if _dyn_min < c_min_time {
    c_min_time = _dyn_min;
}
```

效果（`wave_min_time = 240`）：

| 本波敌人数 | 新的最短停留 |
|---|---|
| 1 | 20 帧 ≈ 0.33 秒 |
| 2 | 40 帧 ≈ 0.67 秒 |
| 7 | 140 帧 ≈ 2.3 秒 |
| 12+ | 240 帧 ≈ 4 秒（不变） |

龙渊/勇士深渊里大量 1–7 只的 subwave，这一条能直接砍掉大半等待。

### 4.3 P0 — 清场即推进（不等 4 秒）

同一个文件，在快进判定之前插入：

```gml
// 场上已无敌人：本轮已经没什么可打，直接把剩余时间压到 12 帧（0.2 秒）
if level_stage == "pre" && current_wave_alive_count == 0 && wave_timer > 12 {
    wave_timer = 12;
}
```

注意放在 `current_wave_alive_count` 计算之后、`wave_timer -= time_ticks_this_step` 之前。

与 4.2 叠加后的整体节奏：

- 波次只有 1 只敌人、出场被秒 → 约 0.2 秒后进下一波
- 波次有 30 只敌人、清空 → 立即进下一波
- 有敌人没死 → 按 `hp_ratio` 快进，或等满 `wave_max_time`

### 4.4 P0 — BOSS 与本波鼠军同时登场（问题 1）

两处改动：

**(a) `objects/obj_battle/Step_2.gml:106-114`** —— 进入 BOSS 波即置标记，不再等「最后一个 subwave + 清光」：

```gml
var _fast_boss_level = _longyuan_full_progression || (string_copy(global.level_id, 1, 13) == "abyss_warrior");
if !_is_tower && level_stage == "pre" && !boss_waiting_clear && current_wave < total_wave && (global.save_data.unlocked_items.elite_unlocked || _longyuan_full_progression || _fast_boss_level) {
    var _main_boss_data = global.level_file.waves[current_wave]
    if _main_boss_data.boss_wave && _main_boss_data.boss != "" {
        if _fast_boss_level {
            // 龙渊 / 勇士深渊：BOSS 与鼠军同场，本波一开始就召唤
            boss_waiting_clear = true
        }
        else if current_wave_alive_count == 0 {
            var _main_boss_sub_total = array_length(_main_boss_data.subwaves)
            if _main_boss_sub_total > 0 && current_subwave >= _main_boss_sub_total - 1 {
                boss_waiting_clear = true
            }
        }
    }
}
```

**(b) `objects/obj_battle/Step_2.gml:116`** —— 让快速关卡跳过「场上必须清空」：

```gml
if boss_waiting_clear && level_stage == "pre" && (current_wave_alive_count == 0 || _is_tower || _fast_boss_level) {
```

> `_fast_boss_level` 需要在 `Step_2.gml` 顶部先定义（第 94 行已有 `_longyuan_full_progression`，紧邻补一行即可）。
> 这样 BOSS 在 BOSS 波第一个 subwave 的同一帧出场，后续 subwave 的小怪继续按原逻辑刷出，形成「BOSS 带小怪」的压迫场面，而不是「先清 60 波小怪再单挑」。

**备选方案（不改代码，只改数据）**：把勇士深渊 3 个 BOSS 波的 subwave 数从 60 砍到 6–8，龙渊从 5 砍到 3。工程量在 json 上，但没有解决机制本身，遇到新关卡还会复发，因此建议以代码修复为主、数据调整为辅。

### 4.5 P1 — BOSS 阵亡后给下一波留间隔

`objects/obj_ly_boss_parent/Destroy_0.gml:17-21`：

```gml
        else {
            level_stage = "pre";
            current_wave += 1;
            current_subwave = 0;
            wave_timer = 3 * 60;      // 新增：给下一波 3 秒喘息
        }
```

同时 `obj_battle_music_controller` 的切歌已经在后面处理，不受影响。

### 4.6 P2 — 可选：subwave 合并

如果希望在数据层根治，可以写一个批处理脚本把「同一 wave 内相邻的、敌人数 ≤ 3 的 subwave」合并成一个：

- 龙渊 631 个 subwave 里，单只敌人的 subwave 有几十个
- 合并后 subwave 数下降，等待时间天然减少

但这会改变出怪节奏（原本一波只放 1 只，现在合成一波放 3 只），需要美术/手感确认，暂不默认执行。

## 7. 验收方式

1. 直接进 longyuan_1_hard，记录 `battle_time` 与每个 subwave 的实际间隔（临时在 `Step_0.gml:337` 打 `show_debug_message` 输出 `current_wave/current_subwave/wave_timer`）
2. 找一个只有 1 只敌人的 subwave（例如 longyuan_2_hard w2 的第 13、17 个 subwave），确认间隔 < 1 秒
3. 进 longyuan_3_hard，确认第一个 BOSS 波（w4）BOSS 与第一批鼠同屏出现
4. 进 abyss_warrior，确认 w2 的 BOSS 不再等 420 只鼠
5. 回归普通关卡（如 camp / volcanic 任意一关），确认 BOSS 波节奏没有被改坏 —— `_fast_boss_level` 为 false 时应完全走原逻辑
